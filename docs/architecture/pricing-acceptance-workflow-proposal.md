# Pricing acceptance workflow proposal

Status: proposal for owner approval. This document does not authorize a migration, commercial expectations, or activation.

## First pricing model

Cloning requires an existing ACTIVE or RETIRED model and therefore cannot create the first DRAFT. Before Task 14, the owner must approve a bootstrap procedure and the commercial model definition. One possible procedure is a reviewed, version-controlled import through an admin-only, AAL2-guarded server operation that validates the complete typed model and creates its DRAFT and rules in one transaction. The procedure must reject duplicate versions and partial imports, record the actor, and use independently approved values. This is a proposal, not authorization to build or execute an import. Synthetic test fixtures must not be imported into the hosted project. The first activation remains blocked until the acceptance workflow and its permissions are independently approved and verified.

Store each manifest revision as an immutable record linked to a pricing model ID and the fingerprint of its validated definition. Record its revision, bounded scenario inputs and independently authored expected catch-up and ongoing money ranges, triggered rule codes, confidence, review flags, and manual-review result. The fingerprint must use a documented canonical serialization shared with the acceptance runner; its relationship to the existing PostgreSQL activation checksum must be specified and tested before integration. Do not store real customer answers as scenarios.

Use a manifest revision table with a UUID primary key, model foreign key, fingerprint, revision, scenario payload, state (`DRAFT`, `APPROVED`, or `INVALIDATED`), author, reviewer, creation time, approval time, and invalidation time. Enforce unique revision per model, bounded payload and revision length, valid state metadata, and reviewer references to staff. A separate append-only event table should record transitions and actors. Changes to scenarios create a new revision; they never rewrite an approved revision. Preserve invalidated revisions and events for audit. Limit indexes to the uniqueness constraint and those required for current approved-manifest lookup after measuring queries.

An active administrator with AAL2 may submit a complete draft for review. An independently authorized reviewer must approve the exact revision and fingerprint after checking its expectations and scenario coverage. The database must confirm active staff status, prevent self-approval if the owner adopts a two-person rule, and record the reviewer and timestamp atomically. The two-person rule and whether reviewer authority is a separate role require owner decisions; do not assume either. Invalid, empty, stale, or failed scenario results cannot be approved. A model edit invalidates prior approval, or equivalently causes every approval lookup to fail on fingerprint mismatch; retain an audit event for explicit invalidation.

The future activation service must load the approved manifest itself, validate and evaluate the exact candidate, then submit the validated projection to the existing guarded activation transaction. The database must lock the candidate and manifest, confirm the approved fingerprint still matches the locked definition, and reject stale or invalidated revisions before retiring the current active model. Establish a consistent lock order for edits, approval, and activation. The existing advisory lock, projection comparison, single-ACTIVE index, and transaction rollback remain mandatory. The current repository blocker and denial of Data API execution remain in force until this integration and its permissions receive separate review.

Use server-only routes under `/admin/pricing/[id]/` for manifest draft, review, and acceptance reports. Every load and action must verify active staff, AAL2, and the required role on the server. Client-submitted pass results or approval identity must never be trusted. Grant no anonymous or ordinary authenticated access to manifest writes or activation; expose only narrowly scoped server operations and apply RLS and explicit function revokes. Review the service-role permissions with the migration rather than granting broad table access.

Required tests include malformed and empty manifests, scenario and fingerprint mismatch, changed candidate after review, unauthorized and AAL1 requests, inactive reviewers, attempted self-approval if required, immutable approved history, duplicate revisions, competing edits and approvals, competing activations, rollback after retirement, and unchanged historical estimate and PDF snapshots. Test SQL grants directly for anonymous, authenticated, and service roles. Use synthetic fixtures only.
